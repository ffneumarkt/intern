# Passkeys (Phase 3) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Members log in with a passkey first and a password as fallback, and manage their passkeys under Einstellungen.

**Architecture:** `internal/passkey` adds four routes on top of `go-webauthn`, with begin and finish linked by a short-lived in-memory session. Login ends in PocketBase's own `RecordAuthResponse`, so tokens, the JS SDK's auth store and the deactivation hook all work unchanged. The frontend uses `@simplewebauthn/browser` for the browser ceremony and the records API to list, rename and remove.

**Tech Stack:** `github.com/go-webauthn/webauthn` v0.18.2, `github.com/descope/virtualwebauthn` v1.0.5 (tests only), `@simplewebauthn/browser` 14.0.0, PocketBase v0.40.6.

**Spec:** `docs/superpowers/specs/2026-10-29-intern-platform-design.md` (sections 3 `passkeys`, 5, 8 Settings, 11 `internal/passkey`).

## Global Constraints

- UI text German only; code, comments and identifiers English.
- Go logging only through `internal/logging`.
- Routes: `POST /api/passkey/register/begin`, `/register/finish` (authenticated), `/login/begin`, `/login/finish` (public, discoverable credentials, no username).
- Login returns the same response as a password login. Session data lives in memory with a 5-minute expiry.
- Relying party ID `intern.ffneumarkt.at`, origin `https://intern.ffneumarkt.at`, configurable for local development.
- The sign count is updated on each login; a sign count regression rejects the login.
- Forms use `components/Field.tsx`; data pages use `useResource`.
- `make test` is the gate on any task touching both sides.

## Verified by spike (2026-10-30, go-webauthn v0.18.2, virtualwebauthn v1.0.5)

- **The backup flags must be stored.** With `BackupEligible` not kept on the credential, the login fails with "Backup Eligible flag inconsistency". Every synced iCloud and Google passkey sets that flag, so the spec's `passkeys` fields would break them on the second login. Store `backup_eligible` and `backup_state`, and restore them through `CredentialFlags`.
- **A regression is not an error.** `FinishDiscoverableLogin` returns success with `Authenticator.CloneWarning == true`; our code must reject it, and must not save the count.
- A sign count of 0 on both sides (synced passkeys) gives no warning, so such passkeys keep working.
- `BeginDiscoverableLogin` and `FinishDiscoverableLogin(handler, session, request)` work end to end against `virtualwebauthn`. Set `auth.Options.BackupEligible = true` and `BackupState = true` to behave like a synced passkey.
- `creation.Response` and `assertion.Response` marshal to the JSON `@simplewebauthn/browser` expects as `optionsJSON`, and to what `virtualwebauthn.ParseAttestationOptions` and `ParseAssertionOptions` read.
- From phase 2: every token issuer passes through `OnRecordAuthRequest`, so `RecordAuthResponse` already rejects deactivated users.

## Decisions on what the spec leaves open

- The user handle is the bytes of the PocketBase user id.
- Credential id is stored base64url, public key base64, AAGUID hex.
- `passkeys` also gets `created`, because Settings shows "angelegt am".
- User verification `preferred`, attestation `none`, resident key `required`, existing credentials excluded on registration.
- All login failures answer the same 400 `Failed to authenticate.`, including regression and deactivation. The reason is logged at `warn`.
- Removing the last passkey is allowed: the password still works.
- Local development needs `localhost:5173`: WebAuthn does not accept an IP address as relying party. `make dev-api` sets the env vars; on `127.0.0.1:8090` passkeys fail by design.
- A pending session store is capped at 1000 entries, oldest dropped, because `login/begin` is public.

## Review Focus

1. A synced passkey (backup flags set) must work on the second and later logins. Test: Task 3.
2. A deactivated user must not get in with a passkey, and must not be able to add one. Test: Task 3.
3. A finish request replayed, expired, or carrying another user's session must fail. Test: Task 2, Task 3.
4. A passkey removed under Einstellungen must stop working at once, and a credential may only log in as its owner. Test: Task 3.
5. Cancelling the browser's passkey dialog is not an error, and a browser without WebAuthn offers no passkey button. Test: Task 4, Task 5.
